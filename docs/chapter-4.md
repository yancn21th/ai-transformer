# 第 4 章 RD 方法论与基础设施

## 学习目标

- 理解一个团队在 AI 时代最先要搭好的基础设施是什么
- 认识 RD 方法论不只是工具堆砌，而是框架、技能、评测和工作流的组合
- 理解为什么“简单+简单”能通往稳定交付，而“复杂+复杂”通常通往失败

## 核心内容

如果前面三章回答的是“为什么时代变了”，这一章回答的就是“团队到底该怎么落地”。真正进入 AI 研发之后，很多团队最容易犯的错，不是工具不够多，而是顺序错了。还没想清楚基础设施，还没搭好模型和执行入口，就急着讨论工作流；还没形成方法论，就急着追最新 Agent 框架；最后往往看起来很先进，实际却很难复用。

所以这一章我想讲三个层次：第一，团队最先要搭好的基础设施；第二，RD 方法论和框架到底应该怎么理解；第三，个人在实践里最重要的心得是什么。

## 第一部分：团队先搭基础设施

### 1. 先选好 LLM，而不是先追热点

一个团队进入 AI 研发，第一步不是“先装一堆 Agent 工具”，而是先确定底层模型策略。因为后面所有的代码生成、任务拆分、上下文理解、工具调用和结果质量，最终都受底层模型能力影响。

如果目标是 AI Coding，那么最值得优先关注的是那些编码能力、长上下文能力和工具使用能力都比较强的模型。例如：`Claude 4`、`GPT-4.1`、`o3`、`Gemini 2.5 Pro`、`DeepSeek-V3 / R1`、`Qwen3-Coder` 这一类模型。它们各自侧重点不同，有的更强在代码理解和重构，有的更强在推理与规划，有的更适合成本敏感场景。团队真正要做的不是争论“谁最强”，而是根据任务类型、成本预算、延迟要求和可用性，选出一到两个主力模型。

### 2. 再选 Code Agent 入口

模型只是发动机，真正进入研发流程的，是 Code Agent 工具。你提到的这几个就是最典型的入口：`Claude Code (CC)`、`Codex / OpenAI Code`、`VS Code Copilot`。这类工具解决的不是“模型有没有能力”，而是“模型怎么进入日常开发现场”。

- `Claude Code` 更像命令行里的工程执行器，适合直接在项目上下文里做修改、搜索、重构和验证。
- `Codex / OpenAI Code` 更偏 OpenAI 体系下的代码执行与任务代理入口。
- `VS Code Copilot` 更适合嵌入编辑器工作流，在补全、对话、修改和多人协作环境里发挥作用。

它们的差别不只是交互界面不同，更重要的是上下文组织方式、权限控制方式、工具调用方式和团队接入成本不同。

### 3. 基础设施的本质是“模型层 + 入口层”

所以团队最先要搭好的，不是华丽的多智能体系统，而是两层基础设施：

1. 稳定可用的 `LLM 层`
2. 能进入真实研发流程的 `Code Agent 层`

没有这两层，后面所有方法论都会停留在 PPT；这两层搭稳了，后面流程和规范才有落地空间。

## 第二部分：RD 方法论和框架

基础设施搭好之后，问题才真正开始。因为工具能用，不代表团队会用；模型很强，不代表结果稳定。RD 方法论的价值，就在于把“个人偶尔用 AI 做出效果”变成“团队持续稳定地产生结果”。

这里可以结合 [awesome-agent 中文清单](https://github.com/fancn21th/awesome-agent/blob/main/README_zh.md) 来看。那份清单有一个很重要的启发：AI 工程不是单一工具，而是一整套生态。里面不是只有模型和工具，还有 `框架`、`技能`、`Evals`、`教程`、`LLM 排行榜`、`工具`、`平台` 这些维度。这恰恰说明 RD 方法论的重点，不是“你用了哪个 agent”，而是你有没有把这些维度组织成一个工程体系。

### 1. 框架：把经验变成结构

像清单里的 `Get Shit Done`、`Superpowers`、`gstack` 这类框架，本质上都在做同一件事：把零散经验变成稳定结构。也就是说，不再依赖某个高手临场发挥，而是把 prompt、上下文、任务拆分、子智能体协作、验证和提交方式变成可复用的框架。

### 2. 技能：把个人能力变成系统能力

清单里的 `Agent Skills`、`Anthropic Skills`、`Matt Pocock Skills` 等资源说明了一件事：未来团队最值钱的，不只是有人“会用 AI”，而是能不能把这种会用，沉淀成团队共享的 Skill。这样 AI 才不是某个人的外挂，而是团队的公共能力。

### 3. Evals：把“看起来行”变成“真的行”

很多团队部署 AI 最大的问题，不是没有生成结果，而是没有验证机制。awesome-agent 里专门有 `Evals` 和评测资源，这提醒我们：AI 系统如果没有评测、观测和回归验证，就很容易停留在 demo 状态。RD 方法论里最容易被忽视、但最关键的一层，就是 evaluation。

### 4. 教程与研究：把局部经验接入更大范式

清单里的 `Building Effective Agents`、`Effective Context Engineering for AI Agents`、`Harness Engineering` 这些材料，其实都在告诉我们同一个方向：真正重要的不是“模型多聪明”，而是“上下文怎么组织、流程怎么编排、系统怎么保持可控”。这和前一章的结论是一致的。模型不是银弹，工程编排能力才更接近银弹。

### 5. RD 方法论的落点

如果要把这一套压缩成几个关键词，我会把它总结成：`Spec`、`Skill / MCP`、`Workflow`、`Evals`。

- `Spec`：先把目标、边界、约束和验收写清楚。
- `Skill / MCP`：把可复用能力变成 Agent 可以调用的工具和接口。
- `Workflow`：把需求、实现、验证、修正组织成闭环流程。
- `Evals`：让系统可以被持续判断、持续比较、持续改进。

这四个词，基本就是团队做 AI RD 时最核心的框架。

## 第三部分：个人心得

我自己的一个很强烈的体会是：任何事情，`简单 + 简单` 通常可以搞定；`复杂 + 复杂` 往往通向失败。

这句话在 AI 时代尤其重要。因为模型和 Agent 会给人一种错觉：反正它很强，那我们可以一次塞进去一个复杂目标、一个复杂流程、一个复杂工具链，最后它应该能自己搞定。现实通常相反。越是复杂目标叠复杂流程，越容易出现上下文污染、边界漂移、错误积累和不可复现。

所以我越来越相信，真正有效的方法不是追求“一次性解决全部问题”，而是把复杂目标拆成多个简单步骤，把每一步都设计成可理解、可验证、可替换的小环节。简单加简单，最后可以拼成大系统；复杂再叠复杂，最后通常连问题出在哪都说不清。

这也是为什么很多看起来很厉害的多智能体方案最后没跑起来，而一些朴素但清楚的单智能体 + 工具 + 验证流程，反而在真实项目里更稳定。团队需要的不是最复杂的架构图，而是最清楚的控制面。

## 实践

请你拿团队里的一个真实任务，按下面三个层次拆一遍：

1. 这个任务依赖的基础设施是什么？你们选的是哪个模型、哪个 Code Agent 工具？
2. 这个任务有没有明确的 Spec、Skill / MCP、Workflow、Evals？
3. 这个任务现在的做法是“简单+简单”，还是已经走向“复杂+复杂”？

如果你发现一个任务已经进入“复杂+复杂”，最先该做的不是继续加工具，而是先减复杂度。

## 小结

本章的重点，是把 AI 落地这件事重新排序。团队最先要搭的是基础设施：模型层和 Code Agent 入口层；接着要建立的是 RD 方法论：Spec、Skill / MCP、Workflow、Evals；最后要记住的，是一个很朴素但很硬的原则：简单+简单可以搞定，复杂+复杂通常通往失败。
