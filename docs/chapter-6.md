# 第 6 章 词汇表

## 使用说明

这一章把前面各章反复出现的关键术语集中整理，方便你在阅读、备课或团队讨论时快速回查。建议把它当成一份“共同语言清单”：遇到概念混淆时，先回到这里对齐定义，再继续讨论方法和方案。

## 核心概念

### AI Agent

能够基于目标自主调用工具、读取上下文、执行步骤并持续修正行为的系统。它不是单次问答，而是带有执行闭环的智能体。

### Agentic Engineering

围绕 agent 的能力边界、工具接入、上下文治理、流程编排和结果验证建立起来的工程实践。重点不是“会不会用模型”，而是“能不能稳定交付”。

### Vibe Coding

主要依赖直觉、即时反馈和模型生成速度完成开发的工作方式。优点是启动快，缺点是容易在复杂系统里失控，尤其是在需求、验证和上下文管理不足时。

### Harness Engineering

为模型和 agent 搭建“可控执行环境”的工程能力，通常包括工具连接、上下文注入、权限边界、任务分解和验证机制。它强调把模型变成可驾驭的系统部件。

### Spec

对目标、范围、约束、接口和验收标准的结构化描述。Spec 的作用是减少误解，让人和 agent 在执行前对“要交付什么”形成一致预期。

### Workflow

把多个步骤、角色、工具或 agent 串起来的执行流程。一个好的 workflow 不只是自动化，更是把决策点、检查点和失败处理显式化。

### Eval

用于评估模型或 agent 输出质量的一套方法与标准。它可以是自动测试、人工打分、场景回放或规则校验，本质上是在回答“这次结果够不够好”。

## 模型与系统

### LLM

Large Language Model，大语言模型。它擅长理解和生成自然语言与代码，但默认并不具备长期记忆、工具执行和稳定流程控制能力。

### Context

模型当前可见的信息集合，包括提示词、文档、代码片段、历史对话和工具返回结果。上下文质量通常直接决定输出质量。

### Prompt

给模型的输入指令与背景信息。高质量 prompt 不是“花哨措辞”，而是清楚定义任务、边界、格式和成功标准。

### Tool Use

模型或 agent 调用外部工具来获取信息或执行动作的能力，例如搜索代码、运行命令、访问接口或写入文件。它让模型从“会说”走向“会做”。

### MCP

Model Context Protocol，一种让模型以标准方式接入工具、资源和上下文的协议。它的价值在于降低工具集成成本，并提升 agent 系统的可组合性。

## 工程方法

### SDD

Spec-Driven Development，以规格为中心驱动实现的开发方式。先定义问题和验收，再组织实现，可以显著降低 AI 辅助开发中的返工率。

### SOP Workflow

把标准操作程序写成可重复执行的工作流，让人和 agent 都能按同一套路推进任务。它适合稳定场景，尤其适合需要多人协作或持续复用的流程。

### Verification

针对输出结果进行验证的动作，例如测试、构建、静态检查、人工复核等。Verification 是 AI 工程里的硬约束，没有验证就没有真正的交付。

### Human in the Loop

在关键节点保留人工判断、确认或兜底机制。它不是“手工低效”的代名词，而是控制风险、提高可靠性的设计方式。

## 组织与协作

### One-Person Company

借助 AI 和 agent，把原本需要多人配合的部分工作压缩到单人可编排的组织形态。它依赖的不是个人蛮力，而是流程、资产和自动化程度。

### AI-Native Team

默认把 AI 当成日常工作系统组成部分的团队。它的区别不在于偶尔使用工具，而在于需求、开发、验证和协作方式都围绕 AI 重构。

### Shared Language

团队内部对关键术语的统一定义。共享词汇表看似基础，实际上决定了讨论效率、协作质量和 agent 指令的一致性。

| MCP | 模型接入工具和上下文的标准协议 |
| Spec | 对目标与验收标准的结构化说明 |

## 小结

如果前五章帮助你建立了理解 AI Agent 时代的认知框架，那么这一章的作用就是把这些框架里的关键词固定下来。真正高效的 AI 协作，往往不是因为大家“都很懂”，而是因为大家对关键概念有一致定义。
