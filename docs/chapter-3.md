# 第 3 章 旧经验还有效吗

## 学习目标

- 重新审视传统研发经验在 AI 时代的有效性
- 理解为什么调 bug 和控制复杂度反而变得更重要
- 掌握“做简单、简单+简单”的工程判断

## 核心内容

面对 AI，很多人会问：旧经验还有用吗？老的最佳实践是不是都过时了？一个更准确的回答是，旧经验没有消失，但它们的作用位置变了。

以前很多最佳实践，是为了帮助人更稳定地写代码。现在部分“写”的动作被 AI 接管了，于是有人误以为规范、架构、分层、测试这些都不重要了。实际恰恰相反。因为生成速度变快之后，系统会更快地变复杂；而一旦复杂度上去，bug 会更难定位，责任也更难切分。你在纲要里提到“bug 不好解决”，这正是 AI 时代最典型的痛点之一。

过去人写错，通常能回忆自己是怎么写错的；现在 AI 写错，问题往往出在提示、上下文、工具结果、历史状态或隐含假设，错误源变得分散。于是旧经验里最有价值的那部分，不是某一条语法级建议，而是控制复杂度的原则。

这里最值得保留的一条就是：`做简单，简单+简单。` 这句话看起来朴素，但它几乎是 AI 时代最重要的工程纪律。因为 Agent 很擅长把局部事情做出来，却不天然擅长替你维持长期可理解性。如果一个系统每一层都让 AI 自由发挥，很快就会得到一个“能运行但没人敢动”的结果。

## 哪些旧经验依然有效

### 1. 分解问题

复杂系统仍然需要拆成多个清晰的小问题，否则你无法验证每一步是否正确。

### 2. 限制边界

越能清楚定义输入、输出和失败条件，AI 生成的结果越稳定。

### 3. 让系统保持简单

不是追求“少功能”，而是追求每一层职责清楚、推理路径短、错误容易定位。

## 哪些经验需要升级

### 1. 调试方式

调 bug 不再只是看代码逻辑，还要看提示、上下文、工具返回和中间状态。

### 2. 最佳实践的载体

以前很多经验写在团队 Wiki 或代码规范里；现在它们还需要进入 prompt、spec、workflow 和 agent skill 中。

## 实践

回顾一个你最近用 AI 写代码时遇到的问题，试着回答：

- 是代码本身错了，还是上下文错了？
- 是需求没说清，还是边界没限制住？
- 如果把这个任务拆成两个更小的步骤，是否更容易定位问题？

## 小结

本章的重点是纠正一个误区：AI 没有让工程纪律失效，而是让复杂度控制、边界设计和调试能力变得更重要。旧经验不是没用了，而是必须升级成适合 Agent 时代的新形式。
